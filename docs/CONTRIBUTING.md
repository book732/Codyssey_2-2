# 기여 가이드

## 브랜치 전략 (GitHub Flow)

브랜치는 특정 커밋을 가리키는 이름입니다. 작업별 브랜치를 나누면 다른 팀원의 작업과 구분해 수정하고 검토할 수 있습니다.

- `main`: 확인된 파일과 문서가 깨지지 않는 상태로 유지하며, 직접 작업하거나 푸시하지 않습니다.
- `feature/*`: Issue별 작업 브랜치로 사용합니다. 최신 `main`에서 분기하고, 작업이 끝나면 PR을 통해 `main`에 병합합니다.
- PR은 다른 팀원 1명 이상의 승인을 받은 뒤 병합합니다.

### 브랜치 네이밍 규칙

Issue 하나마다 최신 `main`에서 브랜치를 하나 만듭니다. 이름은 `feature/<github-id>-<task>` 형식을 사용합니다.

- `<github-id>`: 작업자의 GitHub 사용자 이름을 소문자로 적습니다.
- `<task>`: 작업 내용을 소문자 영문, 숫자, 하이픈으로 짧게 적습니다. 공백과 한글은 사용하지 않습니다.
- 하나의 브랜치에서는 해당 Issue의 작업만 진행합니다. 완료 후 PR을 병합하면 브랜치를 삭제합니다.

예: `feature/book732-team-intro`, `feature/book732-github-flow-guide`

### 이 방식을 선택한 이유

네 명이 동시에 작업하므로 작업별 브랜치를 분리해 `main`을 안정적으로 유지할 수 있습니다. PR에서 변경 내용을 검토하고 승인한 뒤 병합하면 각 작업의 담당자와 수정 과정을 추적할 수 있습니다.

### 커밋 메시지 컨벤션

첫 줄은 `<type>: <summary>` 형식으로 작성합니다. `<summary>`는 변경한 내용을 영어 명령형으로 간결하게 적고, 마침표는 붙이지 않습니다.

| type | 사용 시점 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat: add team profile index` |
| `fix` | 오류 수정 | `fix: correct broken profile link` |
| `docs` | 문서 작성·수정 | `docs: add commit message convention` |
| `chore` | 설정·정리 작업 | `chore: update gitignore` |

`update`, `fix`처럼 한 단어만 적으면 무엇을 바꿨는지 알 수 없으므로 피합니다. 예를 들어 `update` 대신 `docs: clarify branch naming rules`, `fix` 대신 `fix: correct broken profile link`처럼 변경 내용을 명시합니다.

한 커밋에는 한 가지 목적의 변경만 담습니다. 관련 Issue는 PR 설명에 `Closes #이슈번호`로 연결합니다.

## PR 작성과 병합

- 작업은 Issue로 만들고, PR 본문에 `Closes #실제이슈번호`를 적습니다.
- 여러 명이 함께 쓰는 Issue는 `Refs #번호`로 연결하고, 본인 작업의 Issue를 따로 만들어 `Closes`로 연결합니다. 다른 사람의 작업까지 끝나기 전에 공유 Issue를 닫지 않습니다.
- 본문에는 **변경 사항(What), 변경 이유(Why), 확인 방법과 결과(How)**를 적습니다. 확인하지 못한 내용은 그대로 밝힙니다.
- 관련 문서를 어떻게 갱신했는지도 적습니다. 추가 갱신이 필요 없다면 이유를 한 줄 적습니다.
- [PR 양식](../.github/PULL_REQUEST_TEMPLATE.md)을 사용하고 다른 팀원에게 리뷰를 요청합니다.
- 다른 팀원 1명 이상 승인 후 팀장과 확인해 병합합니다. 본인 PR의 승인을 대신 기록하지 않습니다.

## 코드 리뷰

- 각 PR에는 변경 파일이나 내용을 근거로 한 실질적인 코멘트를 1개 이상 남깁니다. `LGTM`, `좋아요`만 남기지 않습니다.
- 예: “README에 소개 링크도 추가하면 찾기 쉬울 것 같아요. 같이 넣어주실 수 있나요?”
- 작성자는 답글을 달거나 수정을 반영해 리뷰어와 최소 한 번 상호작용합니다.
- 각자 PR 생성·병합 2개 이상, 다른 사람 PR 리뷰 2개 이상, 본인 PR의 리뷰 반영 1회 이상을 남깁니다. 리뷰 반영은 수정 커밋이나 답글에서 확인할 수 있게 합니다.
- 본인 소개에 기여한 커밋 1개 이상, Git 트러블슈팅 기록 작성 참여 1회 이상도 필요합니다. 실제 링크는 [SUBMISSION.md](../SUBMISSION.md)에 모읍니다.

## 충돌이 나면

1. 충돌한 브랜치와 파일을 상대 작업자에게 알립니다.
2. 서로 어떤 내용을 남길지 정합니다. 어렵다면 팀장에게 도움을 요청합니다.
3. 함께 내용을 합치거나 하나를 선택하고, 충돌 마커를 제거합니다.
4. 최종 파일과 링크를 확인하고 충돌 해결 커밋을 만듭니다.
5. 해결한 사람이 참여자, 실제 명령과 결과를 [충돌 해결 기록](conflict-resolution.md)에 남기고, 제출물 인덱스에도 링크를 추가합니다.

팀 전체가 충돌 해결 2회 이상을 기록하며, 그중 1회는 같은 hunk(인접한 줄)를 서로 다르게 바꾸거나 파일 이동·삭제와 내용 수정이 겹치는 비자명 충돌이어야 합니다.

## 작업할 때 문서도 함께 갱신하기

이 규칙은 팀원과 AI 도구를 사용한 작업에 모두 적용합니다.

| 바뀐 내용 | 함께 갱신할 문서 |
| --- | --- |
| 팀원 소개 | README의 소개 링크, SUBMISSION의 본인 항목 |
| 파일·폴더 사용 방법 | README 또는 해당 폴더의 안내 |
| 협업 규칙 | 이 문서 |
| 실제 충돌 해결 | 충돌 해결 기록, SUBMISSION |
| 실제 Git 트러블슈팅 실습 | 트러블슈팅 기록, SUBMISSION |
| Issue·PR·리뷰·증빙 | SUBMISSION의 관련 링크와 상태 |

- 현재 상태와 실제 링크만 적습니다. PR 주소는 생성한 뒤 본인 행에 추가해 같은 브랜치에 반영할 수 있습니다.
- 실습 전에는 기록 양식의 빈칸을 유지합니다. 실제로 하지 않은 실습이나 받지 않은 승인, 병합되지 않은 PR을 완료로 표시하지 않습니다.
- PR 병합 후에는 작성자가 완료된 Issue의 체크리스트와 제출 인덱스에 적은 상태를 확인합니다. 다른 사람의 완료 항목은 임의로 바꾸지 않습니다.
- AI를 쓸 때는 [AGENTS.md](../AGENTS.md)와 이 문서를 먼저 읽도록 요청합니다. 팀원은 AI가 수정한 내용과 증빙도 직접 확인합니다.

## Git 실습 시 주의할 점

공유 브랜치의 히스토리를 재작성하지 않습니다. 팀 합의 없이 강제 푸시하거나 리베이스하지 않습니다.

`amend`, `reset --soft HEAD~1`은 원격에 올리지 않은 본인 커밋으로 연습합니다. 이미 원격에 올린 커밋을 취소할 때는 개인 `feature/*`에서 `revert`로 새 취소 커밋을 만들고 PR로 반영합니다.

`stash`와 `stash pop`까지 네 가지 실습을 팀에서 나누어 수행하고, 각자의 역할과 결과는 [트러블슈팅 기록](troubleshooting-log.md)에 남깁니다.
